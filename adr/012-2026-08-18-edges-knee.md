# ADR 012 — The edges knee, closed; and the incremental delete behind it

- **Status:** Accepted. Edges closed as a scaling question (2026-08-17); the incremental delete closed (2026-08-18).
- **Decided:** 2026-08-18
- **Recorded:** 2026-08-19, backfilled from `IMPLEMENTATION_PLAN.md`
- **Evidence:** [`PLAN-EXCERPT.md`](proposals/edges-knee/PLAN-EXCERPT.md) · [`EVAL.md`](proposals/edges-knee/EVAL.md) · `FINDINGS.md` §2.3–2.4 · `eval/results/e1-scan-verdict.json`, `e1-ladder-verdict.json`, `e1-hoist-verdict.json`

## Context

ADR 011 fixed the write phase and left one phase beating its projection in the wrong direction:
**edges, +21.7%**. The `edges` cost *per edge* was flat through T5 and then climbed 3× by T9.

### E1-EDGES was registered and retired the same day — without measuring anything

The question was whether that rise is SQLite page-cache capacity (bounded, already crossed at
target scale) or algorithmic (unbounded). It was retired before any run, because **E1-AB had
already answered it on the same corpus with a stronger arm**, and its data had been sitting
committed and unread for four days: a 512× cache span changes the T5→T9 growth ratio from 3.287
to essentially nothing, and at T9 A/B = **1.0103**, D/B = **1.0202**. By E1-EDGES' own registered
rule that is **ALGORITHMIC**.

Retiring it is recorded here as a decision, not as an absence. It is also the reason ADR 010
rule 2 exists — reading `FINDINGS.md` §1 before writing a registration is now mandatory.

## Decision

**The `files` prefix scan was the exponent. Remove it, and the phase is linear.**

- **E1-SCAN** (2026-08-17): removing the scan takes edges from b = 1.4382 to b ≈ 1.0–1.1;
  T8→T9 local slope **2.4709 → 1.1051**, at 24 runs with T1/T5 controls null.
- **E1-LADDER** (2026-08-17): post-fix **b = 1.0184** (all_runs, n = 27, R² 0.9817,
  `se_hc3` 0.0351) against a pre-fix **1.3814** on the same nine rungs. Leave-one-rung-out spans
  **[0.9944, 1.0449]**, so b ≈ 1.02 is quotable to three figures. E1-SCAN's four-rung estimate is
  **superseded, not contradicted**.

That also killed a hypothesis inferred from a *model*: "something other than the scan is also
super-linear in edges" came from a two-term model's misfit. E1-LADDER measured it instead, and
the misfit was a property of the model, not of the code.

### Stage 4.6 — the FTS guard fixed cold builds, and only cold builds

ADR 011's guard skips the delete when the file was **never indexed**. A cold build has no
existing files, so it skips 100% of them — which is exactly why `fts_del` is 0 ms in all 27
E1-VERIFY runs. **Re-indexing a *changed* file still ran both full-scan deletes**, and a changed
file is by definition already indexed: the defining case of incremental work.

The fact was already known in three places — `e1-fts-verdict.json`'s own `what_this_is`, a CLI
refusal, and a test pinning the behaviour. **None was connected to the "O(changed files)"
claim.** That is the failure: not a missing measurement, a missing join between three recorded
facts and a claim they contradicted.

**The magnitude, measured** on real E1 corpora, one changed file: 3.0 ms at T1, 18.2 ms at T5,
95.6 ms at T8, **151.6 ms at T9**. OLS on log-log **b = 1.32, R² = 0.9975**, projecting **384 ms
per changed file at 150k chunks**. This refuted Stage 4.5's "379 ms for one file **at any corpus
size**" — the magnitude is plausible, the *invariance* was the error, and the invariance was the
load-bearing half. The figure carried no citation anywhere in the plan.

**The fix**: record the contiguous rowid block each file owns (`chunk_fts_lo/hi`,
`ident_fts_lo/hi`), because a rowid is the one column FTS5 will seek on.

A first design using `WHERE rowid BETWEEN ? AND ?` was **refuted by measurement before any code
was written**: FTS5 reports a rowid range as `SCAN ... INDEX 0:=`, and the operative word is
`SCAN` — **75.96 ms** against **75.01 ms** for an unconstrained scan. Only exact equality seeks,
so deletes are issued one rowid at a time: **1.125 ms against 129.8 ms** for one 11-chunk file
at T9.

| corpus (synthetic) | rows | scan arm | block arm | speedup |
|---|---|---|---|---|
| T1~ | 3,684 | 0.85 ms | 0.116 ms | 7× |
| T9~ | 73,362 | 15.14 ms | 0.087 ms | **174×** |

scan arm **b = 0.97** (R² 0.9992); block arm **b = −0.09** (R² 0.9920). **The corpus-size
dependence is gone, not reduced.**

`removeDeletedFiles` got the same block-driven delete, reading the block from `files` before
that row is removed — FTS5 virtual tables do not participate in the foreign-key cascade, so the
deletes must be explicit.

## Consequences

- Edges is closed as a scaling question.
- Incremental re-index no longer pays a corpus-sized cost per changed file.
- E1-LADDER's H3 produced ADR 010's "do not register a bar finer than its statistic can resolve".

## What this does not claim

Stated by confidence class, because they differ:

- The scan mechanism is **measured** (E1-FTS, exponent 2.3454, 91.7% of T9 write).
- Its magnitude on the incremental path is **measured** on real E1 corpora.
- The fix's *shape* — one arm scales with the corpus, the other does not — is **measured**, but
  on a **synthetic** corpus whose constants run ~10× smaller than the real one (15.14 ms against
  151.6 ms at T9) and whose scan-arm exponent is 0.97 against the real 1.32. "Incremental
  re-index is now O(changed file)" is measured for the shape and **inferred** for the constant
  on a real repository.
- Incremental re-index cost on a real 150k-chunk corpus is **unmeasured**. No eval harness
  measures it, and this work did not change that.
